# HapticLab ledger

Every claim this app rests on, and what earned it. The convention is the one
[`SensorLab/Docs/LEDGER.md`](../../SensorLab/Docs/LEDGER.md) uses, which in turn
took it from the hardware-config-recovery investigation in the SDK's `research`
branch, because it is the only one that survives an app growing.

| Tag | Means |
| --- | --- |
| **CONFIRMED** | Measured directly, on this hardware or in a test that exercises the real code, and the method is recorded here. |
| **LIKELY** | Corroborated indirectly: inferred from another measurement, or from documentation that is itself unverified. Good enough to design against, not good enough to state as fact. |
| **UNVERIFIED** | Assumed. Nobody has checked. The row says what would check it. |
| **REFUTED** | Checked and found false. Kept, because a claim that was once believed and is now known wrong is worth more on the record than deleted. |

Rows are dated. A row with no date has not been checked since it was written.

---

## 0. The state of the instrument, in one paragraph

**HapticLab has never been run on the watch, and no perceptual number in this
repository has ever come from it.** What exists is the instrument: the vibro
surface is mapped, the candidate set is generated and well-formed, the protocol
runs end to end in tests, every screen is drawn and disc-masked, the run
directory is written and closed out, and the report generator turns a run into
the report. Every row in §3, §4 and §5 below is UNVERIFIED, and §5 is the
question the app exists to answer. **The first hardware session is what changes
this section.**

---

## 1. The vibro surface

A vibro-stop message would change it. | 2026-09-08 |
| V4 | **Completion means accepted, not finished.** Nothing reports a pattern's end, so the app models the duration and Phase 1 checks the model. | **CONFIRMED** | No event type for it in `MessageTypes.hpp`; and the simulator signals `SUCCESS` on the line after the mock's `play()` returns, which itself only logs. | 2026-09-08 |

| V6 | The unnamed effect indices are lower-amplitude variants of the same waveform, so the enum's gaps are an intensity axis. | **UNVERIFIED**, and it is the most valuable thing Phase 0 can settle | The enum skips exactly the indices this would predict, 1, 4, 7, 10 named and 2, 3, 5, 6, 8, 9 not, which is consistency, not evidence. | V9 | A `notesCount` above eight is clamped by the simulator with a warning; the device is unverified. | **CONFIRMED** for the simulator, **UNVERIFIED** for the device | The clamp is in the dispatcher's `REQUEST_VIBRO_PLAY` case. Probe `V5-count-12` sends a count the array cannot hold. | 2026-09-08 |
| V10 | `RequestBuzzerPlay` is a rhythm-and-loudness channel and not a tone channel: ten notes of `{time ms, volume}`, volume documented as 0-100 % but "currently supported only 4 levels (0, 33, 66, 100)", and no frequency field. | **CONFIRMED** | Read from `CommandMessages.hpp`. Deliberately unused here: a buzzer is audible to everyone in the room, which is the opposite of what the eventual product is for. | 2026-09-08 |

## 2. The platform this app is built on

| # | Claim | Tag | Method / what would change it | Date |
| --- | --- | --- | --- | --- |
| P1 | A GUI process can send `RequestVibroPlay` itself. | **CONFIRMED** | `KernelProviderGUI` hands the GUI the whole `SDK::Kernel`, `comm` included, and `FwDump`'s GUI already sends `RequestSetCapabilities` through it. Confirmed again by this app's own ARM link. | 2026-09-08 |
| P2 | **A CustomGUI receives `EventButton` with its own `timestamp`; the SDK's TouchGFX port does not.** `TouchGFXCommandProcessor::handleEvent` converts the event into a key code, forwards only `CLICK`, `PRESS` and `RELEASE`, and discards the timestamp. | **CONFIRMED** | `Libs/Source/Port/TouchGFX/TouchGFXCommandProcessor.cpp`, the `EVENT_BUTTON` case and `handleEvent`. **This is why this app's GUI is a Rust renderer behind CustomGUI rather than TouchGFX**: reaction time has to come from the kernel's own clock, not from an app's read of the time at handling. | 2026-09-08 |
| P3 | `enMusicControl` makes the system eat `HOLD_1S`. | **CONFIRMED** | Hardware behaviour recorded in the repository's `CLAUDE.md`. Inherited, not re-tested. Designed around twice over: music control is disabled through `RequestSetCapabilities`, and nothing in the protocol uses a hold. | 2026-09-08 |
| P4 | A forwarded phone notification buzzes the same actuator this experiment measures. | **LIKELY** | Not measured; there is one vibro. Consequence if true is severe, an unlabelled presentation in the middle of a trial, so `enPhoneNotification` is disabled for the whole run rather than the risk being taken. | 2026-09-08 |
| P5 | `RequestBacklightSet` with `autoOffTimeoutMs = 0` holds the light on indefinitely on hardware, and the SDK simulator's mock blanks within about 50 ms of the same request. | **CONFIRMED** | `BacklightProbe`'s suite 2, measured on the watch 2026-08-27: `t=0` stayed lit for the whole 30-second window, and every finite timeout fired within a few hundred milliseconds of what was asked. The wearer's arm is down between trials and wrist-tilt cannot be relied on, so the screen has to stay readable for the session. | 2026-09-08 |
| P6 | `brightness` is inert on this firmware; only zero versus non-zero matters. | **CONFIRMED** | `BacklightProbe`'s suite 1. Consequence: the app sends 100 and does not pretend to dim. | 2026-09-08 |
| P7 | `getTimeMs()` is device uptime: 32-bit, wrapping at about 49.7 days. | **CONFIRMED** | SleepLab's ledger, from MapManager reading its own log across 25 launches in 10 boots. Every duration in this app goes through one signed-difference helper, and `ARunAcrossTheUptimeWrapBehavesLikeATwinAwayFromIt` drives a whole session starting 4 096 ms before the wrap and compares its stage transitions with a twin away from it. | 2026-09-08 |
| P8 | `open(write, override=false)` positions the handle at offset 0, not end-of-file, so appending needs an explicit `seek(size())`. | **CONFIRMED**, and re-held here | SensorLab's row P6. Re-held by `AppendingKeepsTheHeaderFirstAndEveryEarlierRow`, and checked by mutation: deleting the seek fails that test and the ones either side of it. | 2026-09-08 |
| P9 | `mkdir` is single level, so a parent has to exist before its child can be made. | **CONFIRMED** | Squash's `ImuFileSink::create` says so and works that way; `FwDump` additionally strips a trailing slash before calling it. Both are respected: the GUI makes `Runs` then `Runs/<id>`, and the Service makes `Runs/<id>/imu` only after the GUI has made its parent. | 2026-09-08 |
| P10 | The SDK exposes no free-space query. | **CONFIRMED** | `IFileSystem` has `mkdir`, `file`, `dir`, `exist`, `remove`, `rename`, `copy` and `objectInfo`, and nothing about capacity. Consequence: the caps in this app are self-defence rather than device awareness, and both the cap and whether it was hit are in `session.json`. | 2026-09-08 |
| P11 | Plugging in USB terminates every running app. | **CONFIRMED** | SleepLab's ledger P8. Consequence: `COMMAND_APP_STOP` closes the run out with the reason `stopped-by-kernel` rather than leaving a file nobody closed, and the USB charging screen is deliberately left enabled because it is the one piece of feedback explaining why a session stopped. | 2026-09-08 |
| P12 | The SDK's JSON writer is not safe to pass numbers to: `add(int32_t)` formats with `%ld` so a negative comes out as its unsigned reinterpretation on an LP64 host, and `add(int64_t)` formats through `%g`. | **REFUTED** as a safe path, and inherited | SensorLab's row P15, reproduced there rather than reasoned. ARM is unaffected, which is exactly why it survives. Consequence: every row this app writes is CSV formatted by hand, and no field in any of them is fractional; `TheHeaderIsValidJsonAndCarriesTheEndReason` strips the quoted spans and insists no decimal point is left. | 2026-09-08 |
| P13 | The GUI ticks at 10 fps and pushing a framebuffer costs 21-24 ms, leaving about 78 ms of slack a frame. | **CONFIRMED** | `RustGuiPoc/Docs/FINDINGS.md`, five hardware runs. Consequence: the protocol's timing quantum is 100 ms, which is why every trial records both when the response window was *due* to open and when the frame that opened it actually went out. Reaction time is measured from the second. | 2026-09-08 |
| P14 | Only the inscribed disc is glass: a pixel counts as lit only if its centre is within 119.5 dot pitches of the centre, half a pitch inside the datasheet's active area. | **CONFIRMED** | `BarcodeLayout::pixelIsLit`, which `textkit::Canvas::round` implements. The crate's round-screen tests hold it: nothing outside the disc, nothing past the chord at its own row, and nothing that fits only because the clip removed the end of it. Checked by mutation: moving a hint's angle toward the top of the disc, lengthening a hint label, and pushing the marks onto the rim each fail a different one. | 2026-09-08 |
| P15 | The bezel indicator bitmaps blit corrupt on device, a smear of horizontal dashes where the arc should be. | **CONFIRMED** | `Barcode/README.md`, where it was worked around, reintroduced and fixed again. Consequence: every button affordance here is a solid fill straight into the framebuffer. On a three-alternative forced choice the button mapping *is* the measurement, so this is the most load-bearing drawing in the app. | 2026-09-08 |
| P16 | Bright ink on a dark ground is the only kind proven to render; a black-on-white readout came back as a blank white band. | **CONFIRMED** | `RustGuiPoc/Docs/FINDINGS.md`. This is the glass, not the framebuffer, so the simulator will happily show text the watch will not. | 2026-09-08 |
| P17 | 85 is the first of the three greys to wash out in daylight. | **CONFIRMED** | `Barcode`, which uses 170 rather than something dimmer for its unlit pager marks for exactly this reason. Consequence: no colour named in the renderer is 85. Glyph antialiasing still lands on it, which is the atlas doing its job rather than a load-bearing choice. | 2026-09-08 |
| P18 | 22 to 26 px em is confirmed readable on this glass and 11 to 12 px is detection only; light autohinting snaps vertically only, so SemiBold reads crisper than Regular at small sizes. | **CONFIRMED** | `Docs/TEXT.md` and `TextKit/README.md`, measured by the cartography research and on the host. ## 3. The IMU as a way of timing the actuator

| # | Claim | Tag | Method / what would change it | Date |
| --- | --- | --- | --- | --- |
| S1 | `FUSION_RAW` at a 10 ms period request delivers **99.52 Hz** on this watch, with a modal gap of 10 ms and a worst gap of 36 ms. | **CONFIRMED** | Measured on 2026-09-08 from the six IMU captures Squash pulled off the watch on 2026-09-03 (`Squash/Tests/pulled/*/imu_*.csv`), about 35 minutes of real wrist data: 99.516 to 99.537 Hz across the six, 10 ms modal `dt` in every one, worst single gap 36 ms. Re-measure from a newer capture to falsify. | 2026-09-08 |
| S2 | This app therefore subscribes to `FUSION_RAW` at 10 ms rather than `ACCELEROMETER_RAW`, which is **a deliberate departure from the brief.** | **CONFIRMED** as a design decision resting on S1 and S3 | The brief specified `ACCELEROMETER_RAW` (0x11) and cited SensorLab's 48.48 Hz. Six axes at twice the rate, from a configuration a shipped app in this repository already uses and whose delivered rate is measured, is better on every axis that matters here: an edge is only ever as precise as one sample period. | 2026-09-08 |
| S3 | A requested sample period is not what you get: a 100 ms request is snapped to 80 ms and a 20 ms request is honoured exactly. | **CONFIRMED** | `RustGuiPoc/Docs/FINDINGS.md`, from a four-cell parameter sweep on hardware. This is why the sweep asks for the bottom of the ladder rather than a round number. | 2026-09-08 |
| S4 | **Nothing Phase 1 produces is a waveform.** An LRA carrier is well above 99.52 Hz and aliases, so onset, offset and a relative energy proxy are what the sample-to-sample difference gives and all it gives. | **CONFIRMED** by arithmetic | Nyquist is 49.76 Hz. Stated here so no report can imply otherwise. | 2026-09-08 |
| S5 | The sensor's own timestamp and `getTimeMs()` are the same clock. | **UNVERIFIED** | `DataView::getTimestampUs()` returns the driver's `mTimeStamp` in ms times 1000 plus its microseconds; nothing says it shares an origin with device uptime. The sweep records the play tick from `getTimeMs()` and the samples' own timestamps, so the *duration* between two edges is unaffected either way and only the latency from ask to onset depends on the clocks agreeing. The first sweep is what checks it. | 2026-09-08 |
| S6 | Every effect index 1-127 has a measurable onset. | **UNVERIFIED** | The sweep reports an onset of -1 for an index that played nothing, which is a real result rather than a missing measurement. | 2026-09-08 |
| S7 | `ALERT_750MS_100` lasts about 750 ms and `ALERT_1000MS_100` about 1000 ms. | **UNVERIFIED**, and it is the only independent check the sweep has | Two of the twenty-one named effects state a duration in their own name, and `effects.csv` carries the declared figure beside the measured one so the two can be compared. This is also where `kNominalEffectMs` comes from: the app models an unmeasured effect at 1000 ms because that is the longer of the two durations the enum itself states, which makes every derived timing a ceiling rather than a guess. | 2026-09-08 |

## 4. The instrument's own properties

| # | Claim | Tag | Method / what would change it | Date |
| --- | --- | --- | --- | --- |
| I1 | **A trial screen cannot name, hint at or narrow the pattern about to be played.** | **CONFIRMED** by construction and by test | The frame struct has no field that could carry it, `FrameBuilder` never reads the presented pattern on a trial stage, and `TheTrialFrameIsIdenticalWhicheverMemberWasPresented` compares the frame bytes for all three members of the same triple. Checked by mutation: a frame that leaks the presented pattern's modelled duration fails it. | 2026-09-08 |
| I2 | The presentation window is the same length for every pattern in the set, so how long the screen says PLAYING says nothing about which played. | **CONFIRMED** by construction and by test | Derived as the longest modelled pattern plus a margin, never per pattern. `ThePresentationWindowCoversTheLongestPatternInTheSet` and `TheResponseWindowOpensAFixedTimeAfterTheAsk`. This is a hazard the brief did not name: a window sized per pattern would hand the wearer the pattern's duration through the glass. | 2026-09-08 |
| I3 | Every pair of patterns gets at least twelve test trials at the default pass count, which is the floor the analysis refuses below. | **CONFIRMED** by test | A triple use is worth three trials to each of its pairs, so a pair needs four triples. The planner runs until every pair has been offered `passes` times rather than drawing a fixed count; swept over forty seeds at each set size and pass count, the shortfall is always zero and the excess never more than three. The first attempt drew the fixed count and left pairs with three trials against a twelve-trial floor. | 2026-09-08 |
| I4 | No pattern is presented twice in a row. | **CONFIRMED** by test | The plan interleaves by most-remaining rather than shuffling and repairing; the repair pass was the first attempt and left repeats at the tail, where every remaining trial was the same pattern. | 2026-09-08 |
| I5 | A session that dies at trial 50 leaves 49 usable trials. | **CONFIRMED** by test | Every row is opened, appended, flushed and closed on its own, and `EveryRowIsOnDiskBeforeTheNextOneIsWritten` reads the file back after each one. `NoHandleIsLeftOpenBetweenRows` additionally holds that no FatFs lock slot is leaked. | 2026-09-08 |
| I6 | A run that ended early is a run with an end reason rather than a missing file. | **CONFIRMED** by test | `session.json` is rewritten whole at the close, and the four reasons are `completed`, `abandoned`, `stopped-by-kernel` and `cap-reached`. | 2026-09-08 |
| I7 | The report generator and the tests share one implementation of the statistics. | **CONFIRMED** by construction | `hapticlab-analyse` is built from the same `Analysis/Confusion.hpp` the gtest suite holds, and `hapticlab-report-roundtrip` drives the real binary over a committed synthetic run. | 2026-09-08 |
| I8 | The report refuses to pool a no-contact control with a wrist run. | **CONFIRMED** by test | Pooling a control with the data it controls is the one mistake that would hide the leakage it exists to find, so the tool exits non-zero and says why. | 2026-09-08 |

## 5. The question this app exists to answer

Every row here is UNVERIFIED. **No session has been run.** They are written down
now so the first session can refute them rather than be read in the light of
them.

| # | Claim | Tag | What would settle it |
| --- | --- | --- | --- |
| H1 | How many haptic patterns a wearer can reliably identify on this watch, on this wrist, without looking. | **UNVERIFIED** | The whole app. Nothing in this repository has ever measured it, and no number should be quoted until `Docs/VOCABULARY.md` carries one with its trials. |
| H2 | Rhythm carries most of the discriminability and intensity carries very little. | **UNVERIFIED**, stated so it can be refuted | The `with-amplitude` set exists precisely to let the experiment say that intensity-only pairs fail. The set was not designed to confirm this. |
| H3 | The no-contact control comes out at chance. | **UNVERIFIED** | A `"contact": "table"` run of the same protocol. Any above-chance accuracy there is leakage through hearing or sight and invalidates the contact data by exactly that much; the report says so in as many words when it sees it. |
| H4 | Masking noise does not collapse accuracy. | **UNVERIFIED** | A `"masking": "masked"` run. If accuracy collapses under masking, what was measured is hearing. |
| H5 | Wrist and forearm tactile displays in the literature tend to land somewhere around 2 to 3 bits of information transfer, roughly four to eight reliably identified items. | **UNVERIFIED here, and not this device's number** | Kept as a sanity note only. A result far outside it is a reason to look for a confound, never a reason to tune toward it. It does not go in the vocabulary as anything but this row. |
